## 双人兼任三角色

依据课程“不足三人须兼任并记录贡献”的要求，每条功能线由一人负责规约、实现和自测，另一人独立验收。规约的范围与验收口径需双方评审；自测不能替代交叉验收。

| 成员 | 规约、开发、自测责任 | 交叉验收责任 | 需提交的材料 |
| --- | --- | --- | --- |
| 李非凡 | E1 测验、E4 成绩册、E2 互动 | E3 / E5 / E6 / E7 | 规约、代码/迁移、测试输出、演示、问题单、贡献记录 |
| 陈志康 | E3 论坛、E5 图谱、E6 预览、E7 通知 | E1 / E4 / E2 | 规约、代码/迁移、测试输出、演示、问题单、贡献记录 |
| 共同模块 | 底座接入、知识点契约、容器部署、联调、答辩 | 每项先指定主责，另一位验收 | 单项负责人、接口决策、部署/恢复记录、联合演示 |

共同模块可结对开发，但正式验收时需由非主实现者重建环境并记录检查过程；若双方深度共同实现且独立性不足，在记录中说明限制，不声称完全独立。

## 日常协作

1. 选择一个 OpenSpec 任务，在 Issue 或协作记录中明确 Requirement ID、主责、验收人、交付物和依赖。
2. 先确认接口、状态与数据口径，再做前后端实现；跨模块契约变更必须通知另一人并评审影响。
3. 小步提交，在同一仓库保留实现和测试依据；具体分支策略由双方决定，本批初始化不创建额外开发分支。
4. PR 附实际运行结果，明确测试替身、未执行项及风险；不要粘贴凭据或原始教学数据。
5. 验收人用同一规约新建环境，提出通过/不通过/阻塞；修复后保留原记录并复验。
6. 每个阶段更新 [贡献记录](templates/contribution-record.md)，写明本人兼任的角色，不把 AI 生成的文档或代码自动算作本人完成且验证的工作。

## 风险与处置

| 风险 | 预警信号 | 处置与负责人 |
| --- | --- | --- |
| 底座无法复用 | 无源码/许可不明/只有静态演示 | 共同列缺口，先沟通教师并评审补建范围，不绕过课程主路径 |
| 七模块超过双人工作量 | P0 交叉验收延后或阻塞累积 | 共同暂停 P1，保留 P0、权限和失败路径，不用删测试换进度 |
| 评分和图谱口径漂移 | 页面、Excel、MCP 数值不同 | 李非凡主查评分与汇总，陈志康主查关联和图谱，以同一快照回归 |
| AI 不稳定或预算耗尽 | 限流、失败、无证据内容 | 模型网关显式降级，保留人工流程；共同记录预算与真实调用证据 |
| 任务重复或断线 | 重复成绩/提醒、界面假保存 | 主责补幂等与状态断言，验收人并发、重放与断线复测 |
| 外部部署/服务不可用 | 公网、邮件或转换故障 | 共同明确阻塞与恢复条件，先完成 P0 确定性链路，不冒充线上成功 |
| 隐私泄露 | 日志、导出、录屏含真实身份/密钥 | 立即停止公开传播，按需撤销凭据；脱敏后再提供证据 |
